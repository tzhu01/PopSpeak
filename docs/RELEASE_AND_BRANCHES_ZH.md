# 分支与发布流程

本文面向维护者。面向用户的介绍见[仓库首页](../README.md)。

## 当前状态

- `main` 是唯一长期维护分支，也是 GitHub Pages 的部署来源；无需 `develop` 或 `gh-pages`。
- 源码已经公开，但尚无可供用户下载的正式 Windows Release。应用源码版本为 `0.4.2`，不等于已发布安装包。
- 现有历史便携压缩包不是可公开发布的官方版本：其签名与第三方运行时再分发门禁未通过。不要上传到 Releases 或在 README 中提供下载链接。
- CI 目前仍有 Rust 依赖安全公告需要处理。不要在检查稳定前启用“必须通过检查”的主分支规则，以免把贡献流程锁死；也不能忽略公告来冒充通过。

## 日常分支

1. 从最新 `main` 创建短期分支：`feat/<topic>`、`fix/<topic>`、`docs/<topic>`、`chore/<topic>`。
2. 提交 PR 到 `main`，说明用户影响、风险与验证结果。涉及模型或 DLL 时，附上来源、版本、哈希与许可信息。
3. 合并前检查前端、Rust 与源码审计 CI。涉及界面时附截图；涉及录音和安装时补人工测试。
4. 合并后删除短期分支。Dependabot 分支由其对应 PR 合并或关闭后处理，不批量删除仍在审查中的分支。

Dependabot 的同时开放 PR 数量会限制在每个生态 3 个以内，并对例行更新分组；安全更新仍需及时单独评估。

## 主分支保护计划

`main` 已禁止强推和删除，并要求线性历史。在 CI 恢复稳定后，再启用必须通过 PR 与 `check-frontend`、`check-rust`、`audit` 三项 CI 的规则。站点部署属于发布流程，不应作为所有代码 PR 的必需检查。独立维护者可以保留 0 人强制审批，但仍应自己检查变更；规则具体设置应与当前 GitHub 计划和维护方式相容。

## 正式版本

只用 `vX.Y.Z` 标签触发 Windows Release 工作流。发布顺序：

1. 确认 `main` 的 CI 全绿，更新版本号与变更说明，完成[开源发布清单](OPEN_SOURCE_RELEASE_CHECKLIST.md)的全部阻断项。
2. 在干净克隆中下载已固定哈希的模型/运行时，确认其再分发许可，完成 Windows 10/11 x64 真实录音冒烟测试。
3. 由 CI 使用 GitHub Secrets 中的证书签名程序、安装包和随附原生文件；校验每个签名、包内容、SHA-256、SBOM 与来源提交。
4. 先生成草稿 Release，人工核对资产和说明后才公开。Release 说明至少包括“适用系统 / 新增与修复 / 已知问题 / 文件哈希 / 第三方许可 / 隐私边界 / 安装与升级方法”。

缺少签名、许可、测试或任何质量门禁时，保持草稿，不公开二进制，也不推送会误触发发布流程的版本标签。开发者自建版本可以按 MIT 使用源码，但不能冒充官方已签名发行版。
